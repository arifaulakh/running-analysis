# Running-Coach Harness — Target Architecture

Status: **proposed** (design agreed 2026-08-11). Not yet implemented.
Supersedes the ad-hoc file layout that required hand-editing 5+ files to
switch races (SF Half → Toronto 5K, Aug 2026).

This document is the output of a three-way design debate (minimalist /
determinism / long-horizon-memory lenses) that reached consensus. It
records the target design and a phased migration plan.

---

## 1. The problem

Switching races — **the** recurring lifecycle event — currently means
hand-editing `profile.json`, `plan.yaml` (every calendar date by hand),
`SKILL.md`, `procedural.md`, `phase_guidance.md`, plus an improvised
memory "close-out." Observed failure modes:

1. **Hand-materialized dates.** `plan.yaml` carries an explicit date on
   every day; a wrong weekday breaks the coach's "today's workout" lookup
   silently. Date math, mi→km, and the race-day weekday shift were all
   done by hand in a comment block.
2. **Conflated lifecycles.** `profile.json` mixes durable athlete facts
   (max HR, race history) with per-block config (current race, goal,
   dates), so a switch risks clobbering durable data.
3. **Undefined block transition.** The end-of-block distillation was
   improvised once under time pressure (see the `<!-- BLOCK CLOSE-OUT -->`
   comment in `semantic.md`) — invisible to review, non-repeatable.
4. **Redundant sources of truth.** Max HR lives in both `profile.json`
   and a semantic claim; goal in both.
5. **Numbering cruft.** `proc_011` exists only to patch the week-numbering
   prose in `proc_005/008/010` after a switch.

## 2. Design principles (the consensus)

- **If it has one correct answer, it's code.** Date math, week/weekday
  anchoring, unit conversion, dedup, ID generation — never the model's job.
- **The model owns judgment, not arithmetic.** Coaching prose, run-quality
  reads, claim distillation, "should this be a down week" — the LLM.
- **One canonical home per fact, matched to its consumer.** Facts read by
  code (dashboard, date module, evals) are **typed fields**; facts that are
  judgments are **scope-tagged prose**. The split is by *kind of data*, not
  by file count.
- **Lifecycle, not just storage.** Every claim has a shelf-life
  (`durable` vs `block`) and can be retired. Nothing grows unboundedly.
- **Earn complexity; don't provision it.** Single-user tool: no CI gate
  ceremony, no per-block archive directories, no standing per-run
  subagent, no numeric confidence scores. Add them only when a real pain
  appears.

## 3. Target data model

| File | Owns | Lifecycle | Consumer |
|---|---|---|---|
| `data/athlete.json` | Durable typed facts: `max_hr_observed{value,date,source_activity_id}`, `vdot_history[]`, `race_history[]`, `timezone`, `name`, `easy_pace_model` | Rarely changes; never wiped on a switch | coach, dashboard, code |
| `data/block.json` | Per-block config: `race{}`, `goal_time`, `goal_band`, `plan_template`, `training_start_date`, `plan_weeks`, `deviations[]` (travel weeks, swaps) | **Replaced wholesale** at each transition | coach, generator |
| `data/plan.yaml` | **Generated** materialized calendar: dated weeks, `plan_week`/`strava_week` computed fields, phases | Regenerated by code whenever block.json/template change; never hand-edited | coach, dashboard |
| `templates/<plan-id>.yaml` | **Relative** plan structure (week index, weekday, session type, distance formula) — no calendar dates | Static, reused across blocks and athletes | generator |
| `data/memory/claims.md` | Merged semantic + procedural. Each entry: `[pattern]`/`[rule]` tag, `scope: durable\|block`, text, confidence (categorical), evidence refs, `created_at`, `retired_at` | Retired in place (marked, not deleted) | coach |
| `data/memory/episodic.jsonl` | Append-only event ledger | Forever | coach, debrief |
| `data/runs.jsonl` | One line per run (Strava + freetext merged) | Append-only | coach, dashboard |

Deleted: `profile.json` (→ athlete.json + block.json), `semantic.md` +
`procedural.md` (→ claims.md). Numeric facts (max HR, VDOT, PRs) live
**only** in `athlete.json` — claims.md may *reference* them, never
restate them as a second source of truth.

## 4. Plan as code

- Templates are **relative** (no dates). A generator materializes the
  concrete plan:
  `scripts/generate_plan.ts` reads `block.json` + `templates/<id>.yaml`,
  calls `lib/plan_dates.ts`, writes `data/plan.yaml`.
- `lib/plan_dates.ts` is the **entire deterministic surface** — a small,
  unit-tested module shared by the coach's generation path *and* the
  dashboard's render path (one thing to keep in sync, not two):
  - `dateFor(startDate, weekIndex, weekday)` → calendar date
  - mi→km conversion
  - race-day weekday shift (Higdon's Sunday race → the race's actual day)
  - travel/deviation-week insertion
  - `plan_week` / `strava_week` stamping (kills `proc_011`)
- Correctness comes **by construction** (using the tested function),
  plus co-located unit tests (`yarn test`: week boundaries, DST-adjacent
  dates, race-day-not-Sunday, deviation insertion). **No** separate
  validator suite, **no** CI gate — proportionate to a one-file module.
- `plan.yaml` is still materialized (the dashboard reads it as a file),
  but is generated output, marked `# GENERATED — do not hand-edit`.

## 5. Memory & the block lifecycle

- **Mid-block:** no standing per-run subagent. The coach writes obvious
  durable-truth updates to `claims.md` inline, same turn, as a small diff.
- **Block transition is a required, defined step** (a checklist in
  `SKILL.md`, not a new subsystem), triggered when a goal-race result is
  ingested:
  1. Append the `race_result` to `athlete.json` (`vdot_history`,
     `race_history`) and `episodic.jsonl` — *code*.
  2. **Debrief pass** — one concentrated LLM judgment sweep (the
     repurposed `memory-observer`, invoked **once here**, not per run):
     walk every `scope: block` entry in `claims.md` and, for each,
     *retire* (mark `retired_at`) / *fold into a new durable claim* /
     *promote to an `athlete.json` field*. Write a short debrief note to
     `episodic.jsonl`.
  3. Overwrite `block.json` with the next block's spec; regenerate
     `plan.yaml` — *code*.
- `training-planner` seeds the next block's `goal_band` from
  `athlete.json` + the debrief note.

Why the debrief must be explicit: a "Race History" section captures
*outcomes*, but process claims ("explicit hold-back briefs counter Arif's
run-hot tendency") only exist if something *compares* block-scoped
observations and writes the synthesis down. That synthesis is the thing
that makes race #5 smarter than race #1, and it will not happen by passive
appending — it needs a defined moment.

## 6. Code vs LLM boundary

| Deterministic (code, tested) | Judgment (LLM) |
|---|---|
| date/weekday math, unit conversion | message classification |
| plan materialization from template + spec | run-quality / adherence reads |
| week-numbering fields | claim distillation, retire/promote decisions |
| archival, `block.json` overwrite, file moves | confidence (categorical) |
| dedup, ID generation | coaching prose, race strategy |

## 7. Explicitly rejected (complexity not worth it here)

- Numeric confidence scores (false precision; categorical stays).
- Per-block archive directories (retire in place until size actually hurts).
- A 7-state enforced lifecycle machine.
- A CI validation gate / generator "framework" with standing test infra.
- A standing per-run memory-observer subagent.
- Rendering the plan live at read-time (arithmetic must be code).

## 8. Migration plan (phased, each independently shippable)

- **Phase 1 — Data model split.** `profile.json` → `athlete.json` +
  `block.json`. Update `SKILL.md`, `training-planner.md`, and
  `dashboard/lib/{load,types}.ts` to read them. No behavior change.
- **Phase 2 — Plan as code.** Extract `templates/hal-higdon-intermediate-5k.yaml`;
  write `lib/plan_dates.ts` + `scripts/generate_plan.ts` + unit tests;
  regenerate the *current* 5K `plan.yaml` from the template and diff it
  against the hand-built one to prove parity. This retires the #1 bug.
- **Phase 3 — Memory consolidation.** Merge `semantic.md` + `procedural.md`
  → `claims.md` with `scope`/`[pattern|rule]` tags + `retired_at`; move
  max HR / VDOT to `athlete.json` as the sole home; delete `proc_011`.
- **Phase 4 — Block lifecycle.** `scripts/close_block.ts` for the
  mechanical steps; define the debrief checklist in `SKILL.md`; repurpose
  `memory-observer` to debrief-mode (transition-only).
- **Phase 5 — Tests/evals.** Co-located unit tests for `lib/plan_dates`;
  update eval goldens to the new file layout.

Recommended sequencing: **Phase 1 + 2 remove the actual error surface**
we hit and are worth doing now; Phase 3 + 4 are best built just before the
next race transition (post-Oct-17), when they'll actually be exercised.

## 9. Implementation status (2026-08-11)

**Phase 1 — DONE.** `profile.json` split into `data/athlete.json` (durable:
max_hr_observed, vdot_history, race_history, easy_pace_model, timezone) and
`data/block.json` (per-block: race, goal_band, plan_template,
training_start_date, deviations). Consumers updated: `SKILL.md`,
`training-planner.md`, `phase_guidance.md`, `run_schema.md`,
`dashboard/lib/{load,types}.ts` (typechecks clean; legacy `profile.json`
fallback retained for old snapshots), `README.md`, `.gitignore`.
`profile.json` deleted.

**Phase 2 — DONE.** `templates/hal-higdon-intermediate-5k.json` (relative
structure, no dates), `lib/plan_dates.mjs` (the deterministic surface:
date/weekday math, mi→km, travel-deviation insertion, race-day shift, a
by-construction correctness gate), `scripts/generate_plan.mjs` (generator +
minimal YAML emitter), `lib/plan_dates.test.mjs` (7 tests, `node --test`).
`data/plan.yaml` is now generated and marked `# GENERATED`. Verified: 0
structural diffs vs the hand-built plan across all 63 day-slots; race lands
on Sat 2026-10-17.

**Pragmatic deviations from the idealized spec** (noted so they're not
mistaken for oversights):
- Written as **zero-dependency Node ESM (`.mjs`)** run by `node` / `node
  --test`, not TS — the only TS toolchain is inside `dashboard/` and node
  20.9 can't strip TS types without an added loader. Port to TS if the
  dashboard ever needs to import `plan_dates` directly.
- Template is **JSON**, not YAML, to keep the generator parser-free.
- No standing test runner added; tests run via built-in `node --test`.

**Known follow-ups (deferred):**
- Eval fixtures (`evals/coach.eval.ts` and any staged snapshots) still
  provide `profile.json`; they need migrating to `athlete.json` +
  `block.json` before the coach evals will pass (part of Phase 5).
- No `athlete.json.example` / `block.json.example` yet; fresh clones fall
  back to `profile.json.example` via the dashboard's legacy path.
- Phases 3–5 not started (memory consolidation, block lifecycle, evals).
